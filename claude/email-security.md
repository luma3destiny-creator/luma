# Email protection — local change, not deployed

The sendmail handler previously accepted unauthenticated, unlimited requests.
It now requires a current paid D1 token with a valid future expiry. Charge IDs
and the dev shortcuts cannot authorize sending. The browser supplies its saved
token for both report types and shows failures instead of hiding them.

Proposed initial limits: 60 seconds between attempts, 3 attempts per payment in
rolling 24 hours, 20 attempts globally in rolling 24 hours. These are conservative
starting values, not Brevo plan limits. A single INSERT SELECT reserves the attempt
and rechecks the payment token/expiry. Failed or unknown sends consume quota.
Token rotation does not reset the payment's quota. No recipient or report is
stored in the quota table. Provider response details are not logged.

Before Preview deployment, apply migrations/008_email_send_attempts.sql to
luma-db-preview. Missing table/DB fails closed. Do not run against production
as part of this task. No migration, push, real email or deployment was performed.

Validation: node --test tests/email-security.mjs. Handler with real in-memory
SQLite and intercepted provider fetch; no external send. Burst test uses one
process, not multiple processes or live D1.

Limits: recipients and content still come from the browser; paid users can send
arbitrary content within the quota. This is not recipient ownership verification
or verification that a report was generated by LUMA. Production phone-only
recovery also remains a way to obtain a token until OTP rollout closes it.
Do not claim that token checks alone resolve that existing weakness.
Quota rows accumulate; plan bounded retention cleanup separately if needed.
Provider acceptance is not confirmation of delivery to the inbox.

The new final inline script overrides the legacy minified sendByEmail function;
the legacy function remains in source but is replaced before user interaction.
